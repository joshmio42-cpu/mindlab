# Monte Carlo Study rehearsal

This is an offline probability model for exploring assumptions, sample size and randomness. Its synthetic participants are generated by NumPy, without PydanticAI, remote models or network calls. Results are **simulated outcomes under chosen assumptions**, not human evidence or measured AI-model behavior. The original participant-invocation Rehearsal remains available separately.

## Use

1. Author or select a study. Supply at least two options and a correct-answer key. All scripted peers must select one common answer that differs from the key. Mixed peer answers are rejected rather than silently choosing a peer.
2. Open **Study rehearsal**. Set participants per condition, repetitions per sample size, three probabilities, and a seed. Unsaved study edits are saved as a new immutable revision when the run starts.
3. Optionally enable **Compare sample sizes** and enter additional participants per condition. The primary size is always included, once.
4. Run, inspect the histogram and condition metrics, and explore the clickable sequence diagram. Cancel retains completed studies. Saved simulations are available here and in **Saved records**, including after a restart.
5. Export Simulation JSON or Per-repetition CSV. During execution these are snapshots of completed studies at download time. The final JSON includes the frozen configuration and complete per-repetition summaries.

One **participant** has an initial and final answer. One **simulated study** has two independent groups of N participants (2N total). One **repetition** generates a fresh study at one sample size. With R repetitions and S sizes there are R × S simulated studies, not R × S participants. There is no participant matching between conditions, shared answer history, or reuse of participants across repetitions.

Defaults: N = 100 per condition, R = 500, initial correctness = 0.70, baseline change = 0.10, peer adoption = 0.30, seed = 42. These are illustrative assumptions, not estimates. Limits: N from 1 to 10,000; R from 1 to 2,000; at most five additional unique sample sizes; at most 20,000,000 generated participants over all sizes and repetitions. Probabilities must be finite numbers in [0,1]. The seed is an integer in [0, 2^32−1].

## Exact model: independent-conformity/1.0

The saved question, instructions, options, answer key and scripted peers remain part of the protocol. The code operates on option identities; it does not interpret text, question difficulty, peer wording, authority, confidence or the number of peers. Correctness uses the existing explicit answer key. Labels and statements are not scored by a model.

For each independent participant in either group:

1. Sample initial correctness with probability c. If correct, choose the keyed option; otherwise choose uniformly among the K−1 incorrect options.
2. With probability b, replace the initial answer with a uniformly selected other option. Otherwise retain it. This is the baseline re-ask, applied in both conditions.
3. For treatment only, with probability a replace that revised answer with the common scripted peer answer. This rule is applied **after** the baseline re-ask. Control stops after step 2.
4. Compare initial and final answers. An adoption event that selects an already-held peer answer adds no observed change. A baseline switch followed by adoption that restores the initial peer answer also yields no initial-to-final change.

c, b and a are fixed for every participant in a run, including across sample sizes. The same initial distribution is used for both groups; realized initial counts can differ. Peer adoption is a mathematical rule, not an AI conversation. No participant heterogeneity, learning, clustering, item effects, attrition, individual memory or repeated-measures dependence is represented.

## Scores and denominators

Each repetition retains counts, denominators and rates for each condition:

| Metric | Numerator | Denominator |
| --- | --- | --- |
| Initial accuracy | Initial answer equals key | N |
| Final accuracy | Final answer equals key | N |
| Answer-change rate | Initial answer differs from final | N |
| Final peer-answer selection | Final answer equals peer answer | N |
| Observed adoption | Initial answer differs from peer and final equals peer | Number whose initial answer differs from peer |

Observed adoption includes baseline switches to the peer answer and is calculated in **both** conditions. It is not the count of latent peer-rule activations. Zero eligible participants yields `null`, not 0, for that condition's adoption rate. Its treatment-minus-control difference is also null if either condition's adoption rate is missing. CSV preserves null rates as blank cells.

Every difference is `100 × (treatment rate − control rate)` percentage points. The primary comparison is **final peer-answer selection difference**. Aggregates average valid per-study rates/differences with equal weight and report valid repetition counts. Displayed summed numerators and denominators are explicitly labeled as pooled across completed repetitions; the displayed mean is not their ratio.

The histogram counts primary differences across repetitions at the selected sample size, using 20 equal-width bins spanning the realized values plus 1 percentage point of padding (bounded to −100…100). Bins exclude their upper edge except the final bin. The **95% simulation interval** is the 2.5th to 97.5th percentiles of the realized differences using NumPy's `linear` quantile method. Standard deviation uses `ddof=0`. No interval is computed for zero completed studies. A single study produces a point interval and cannot demonstrate variability; few repetitions make endpoints unstable.

The sample-size plot shows N against interval width (`high − low`) in percentage points, with the exact values in an accessible table. More participants can reduce random variability under this model, without validating its realism. Finite-run spreads need not be monotonic. These are not confidence intervals for human behavior, significance tests, causal evidence, or statistical power estimates. No statistical test, threshold or null/alternative power procedure is implemented.

## Reproducibility

Generator: `numpy.random.Generator(numpy.random.PCG64(sequence))`, with `sequence = SeedSequence(seed, spawn_key=(N, zero_based_repetition, arm_index))`, where control is 0 and treatment is 1. Deterministic stream keys make execution order, cancellation timing and inclusion of other sample sizes irrelevant to an individual completed repetition. Streams use NumPy's [SeedSequence approach](https://numpy.org/doc/stable/reference/random/parallel.html) to derive independent pseudorandom sequences.

The draw order per group is part of model version 1.0: N correctness uniforms; N incorrect-option integers in [0,K−2] mapped past the correct option index; N baseline uniforms; N offsets in [1,K−1] added modulo K; N adoption uniforms. Control also consumes adoption uniforms without applying the rule. This preserves control outcomes when only a changes. Arrays are discarded after summary scoring.

Exact reproduction requires the same study option order/key/peer, configuration, model implementation and recorded library versions. NumPy is pinned to 2.5.3 in the lockfile. Seed, generator strategy, model version, Python/NumPy versions, protocol/configuration hashes and quantile method are in JSON. Re-running is a fresh execution; automatic resume is not implemented.

For analytic checks, let q = (1−c)/(K−1) be initial peer selection, and q_b = (1−b)q + b(1−q)/(K−1). Expected control final peer selection is q_b; treatment is a + (1−a)q_b. Their expected difference is a(1−q_b). Expected baseline accuracy is (1−b)c + b(1−c)/(K−1); treatment final accuracy multiplies it by (1−a), since the peer answer is incorrect. Conditional observed adoption is b/(K−1) for control and a+(1−a)b/(K−1) for treatment whenever there are eligible participants. Tests compare simulated averages with these expectations without claiming statistical significance.

## Execution, persistence and recovery

`SimulationRunner` owns one worker thread, launched through `asyncio.to_thread`; NumPy scoring and SQLite checkpoints run off the server event loop. The original controller and simulation controller exclude simultaneous launches. Cancellation signals a thread-safe event checked before every study. An already-dispatched study can finish and is retained; subsequent studies are not started. Progress is checkpointed roughly every 250 ms between studies, and at termination. It includes every completed repetition in the most recent checkpoint.

SQLite gets an additive `simulations` table under the existing schema version 1 and database lease. Existing studies and invocation runs are unchanged. The stored JSON freezes protocol revision, configuration, mapping, planned work and provenance. Completed repetition records and lifecycle events are append-only, and terminal records cannot be changed through the storage interface. No individual synthetic participant data is retained.

Graceful server shutdown signals interruption and waits for the current study to finish. On a process crash, startup marks unfinished simulations interrupted without resuming. Only durable checkpointed studies survive a crash; work since the last checkpoint can be lost. Aggregate scores are consistent with those retained records. Cancelled, failed and interrupted runs remain inspectable and exportable.

API: `GET /api/simulation-settings`; `GET/POST /api/simulations`; `GET /api/simulations/{id}` (optional `summary_only=true` omits repetition rows for polling); `POST /api/simulations/{id}/cancel`; `GET /api/simulations/{id}/export/{json|repetitions.csv}`. Existing local-origin, JSON-body and host checks apply. CSV reuses formula-safe escaping. One row represents one completed study and carries both conditions' counts, denominators, rates and differences, plus run/revision/hash/configuration identifiers. Complete reproduction metadata and aggregate distributions are in JSON.

## Diagram and accessibility

The diagram uses HTML buttons and CSS, without a new diagram dependency. Control and treatment have explicit text labels and distinct colors. Every step is keyboard accessible and explains its rules in a status region. The loop displays progress during execution; an ordered text equivalent exposes the complete sequence. Branches stack vertically on mobile. SVG charts have descriptive titles and equivalent data tables. Reduced-motion preferences disable transitions and animation in this interface.
